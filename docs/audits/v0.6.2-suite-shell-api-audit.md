# Core v0.6.2 Suite-Shell API Audit

Status: accepted scope recommendation for issue #185
Audit date: 2026-08-19
Milestone: #178 — v0.6.2 Pilot Operations Support and Shared Teacher Setup

## Purpose

This audit is the pre-implementation scope gate for Core v0.6.2.

Its question is intentionally narrower than "what could Core add?":

> Which concrete Phase 1 operations cannot be implemented safely through the public Core 0.6.1 surface, and which of those missing capabilities are genuinely Core-owned?

The audit applies two default rules:

```text
reuse an existing public Core service
before
adding another Core abstraction
```

and:

```text
prove a shared Core requirement
before
creating a shared Core contract
```

The result materially reduces the originally proposed v0.6.2 scope. Core 0.6.1
already exposes substantially more of the required setup, workspace, Academic
Period, scan-routing, and registry behavior than the placeholder issues assumed.

The remaining substantive Core work is concentrated in:

1. guarded roster import preview/diff/commit semantics;
2. failure-isolating diagnostics for Core-defined provider contracts;
3. a neutral module-operations provider family with distinct readiness and
   attention capabilities; and
4. direct Core CLI access only where a surviving Core-owned application
   operation needs it.

This audit does not implement those services.

## Normative ownership and dependency rules

The accepted suite-shell boundary remains controlling.

### Core owns shared authority

Core owns neutral shared state and protocols, including:

- identifiers;
- workspace resolution, validation, initialization, and saved selection;
- class-qualified identity and class metadata;
- rosters and roster-qualified student identity;
- standards;
- active school-year state;
- Academic Period calendars and references;
- PDS2 routing identity and parsing;
- route registration and dispatch;
- retained source-scan custody and generic routing-review metadata;
- Academic Work Registration;
- Publication Records;
- publication-producer compatibility;
- registry/catalog audit and bounded maintenance; and
- deliberately neutral cross-module contracts such as
  `grouping_signal_set_v1`.

### The suite shell owns orchestration and presentation

The suite owns:

- bootstrap/update behavior;
- exact suite release composition;
- `pds doctor` aggregation and presentation;
- PASS/WARN/FAIL/SKIP policy;
- remediation guidance;
- launchability;
- combined teacher workflows;
- backup/restore orchestration;
- mixed-workflow previews;
- aggregated module attention;
- local troubleshooting/event retention; and
- suite-level installed acceptance.

The shell may call public Core mutating services. It must not reproduce Core
validation/storage rules or directly write canonical Core files.

### Modules own domain facts

ScoreForm, Quillan, Concord, Meridian, Vitrine, and Portia remain authoritative
for their own domain records, domain readiness facts, attention facts, repair
workflows, and interpretation.

A neutral shared provider may carry a bounded report from a module. Core must
not decide the truth of a module-specific readiness or attention statement.

### Dependency direction

Preserve:

```text
paper-data-suite -> pds-core
module           -> pds-core, where required
```

Do not introduce:

```text
pds-core -> paper-data-suite
pds-core -> scoreform/quillan/concord/meridian/vitrine/portia
```

## Important integration categories

The following categories remain distinct:

```text
installed distribution
suite-qualified component
launchable application
routing module
publication producer
publication consumer
operations/readiness provider
attention provider
```

`paper_data_suite.modules` is the Core routing-profile entry-point group. It is
not a generic application registry.

`paper_data_suite.publication_producers` is a separate publication-producer
entry-point group.

Neither group establishes launchability, suite support, operational readiness,
or teacher attention.

## Audit method

For each proposed capability the audit traced:

1. the requesting shell/module issue;
2. the canonical owner;
3. current public Core implementation;
4. current tests/documentation where material;
5. whether a consumer would need private imports, direct canonical writes, or
   duplicated validation to proceed;
6. failure and concurrency implications;
7. privacy implications; and
8. whether absence is a hard blocker or an optional interoperability gap.

A missing convenience wrapper is not automatically a Core gap.

## Current Core API inventory relevant to Phase 1

### Workspace

`pds_core.workspace` already provides:

- `resolve_workspace_root(...)`;
- `inspect_workspace_root(...)`;
- `ensure_workspace_root(...)`;
- `save_workspace_root(...)`;
- `clear_saved_workspace_root(...)`;
- `workspace_baseline_dirs(...)`;
- platform-specific user config resolution; and
- default workspace resolution.

`WorkspaceStatus` reports the resolved path, selection source, existence,
directory status, writability, config path, and default root.

`inspect_workspace_root(...)` is non-mutating. Its writability observation uses
filesystem access checks; it does not create a write-test file.

**Conclusion:** workspace diagnosis and ordinary workspace setup require no new
Core service.

### Classes and class metadata

`pds_core.classes` already provides deterministic class-folder resolution and
creation, roster load/write integration, and stable class-folder enumeration.

`pds_core.class_metadata` owns validated class metadata and canonical
persistence.

**Conclusion:** ordinary class creation/metadata setup can be composed from
existing public Core APIs. No generic class-management facade is currently
justified.

### Rosters

`pds_core.rosters` already provides:

- immutable typed `StudentRecord` and `Roster` models;
- strict CSV parsing;
- required-column and row validation;
- class ID validation;
- duplicate `student_id` rejection;
- preservation of extra fields;
- deterministic serialization;
- atomic file replacement;
- add/replace/upsert/remove transformations; and
- structured roster issues/errors.

Identity is the durable `student_id`. Core does not need or permit fuzzy
name-based matching.

What is not present is a first-class full-import operation that:

- compares a candidate complete roster with the current roster;
- reports additions, changes, removals, and unchanged identities;
- binds teacher review to a fingerprint of the current roster; and
- refuses commit if the current roster changed after preview.

**Conclusion:** this is a genuine bounded Core gap and should be the focus of
#187.

### Active school year

`pds_core.school_years` already provides:

- `validate_school_year(...)`;
- `load_school_year_state(...)`;
- `get_active_school_year(...)`;
- `open_school_year(...)`; and
- `close_school_year(...)`.

Writes are atomic file replacements. Opening another year requires an explicit
`overwrite=True`.

The service does not expose a long-lived preview/CAS token. That difference is
not currently a Phase 1 blocker: the proposed suite setup can display the
current state, request confirmation, and immediately invoke the existing Core
operation without reproducing Core semantics.

If future multi-process workflows require a long-lived school-year transition
plan, that should be justified separately.

**Conclusion:** current Phase 1 school-year setup is existing-Core-sufficient.

### Academic Periods

Core already owns the important review/commit safety contract.

The public Academic Period surface includes:

- immutable typed calendars and period records;
- complete calendar validation;
- `validate_academic_period_calendar_transition(...)`;
- exact school-year and revision loading;
- deterministic revision listing;
- an explicit `current.json` pointer;
- immutable revision files;
- write locking;
- `expected_current_revision` conflict protection;
- transition validation during writes; and
- exact Academic Period reference resolution.

Core deliberately does not infer a latest revision or invent a school calendar.

**Conclusion:** the originally proposed Academic Period "planning service" is
not required. A suite wizard may construct/validate a proposed typed calendar,
show it, and call the existing guarded writer after confirmation.

### Standards

Core already exposes the management, validation, profile, starter-pack,
selection, import/export, and atomic workspace persistence behavior required by
the suite's setup workflow.

**Conclusion:** standards setup is existing-Core-sufficient plus suite
orchestration.

### Academic registry health

`pds_core.registry_audit` already exposes public bounded read-only inspection,
including `get_academic_registry_status(...)`, `RegistryStatus`, typed findings,
catalog state/currency, lock counts, temporary-artifact counts, canonical
validity, and optional manifest/producer compatibility checks.

The CLI already exposes bounded `academic registry status` and `validate`
workflows.

**Conclusion:** `pds doctor` can use Core authority for registry health without
a new general registry-health abstraction.

### Routing provider discovery

`pds_core.module_profiles` already provides strict runtime discovery and
registry construction for `paper_data_suite.modules`.

The runtime discovery path loads the entry point, requires a callable provider,
calls it, validates the returned `ModuleProfile`, and fails closed on malformed
providers. Registry construction also rejects duplicate module identities.

That fail-closed behavior is correct for constructing a trustworthy runtime
routing registry.

It is too coarse for a health-oriented caller that wants to report independent
candidate outcomes without losing all diagnostic visibility after one broken
optional provider.

**Conclusion:** a separate failure-isolating diagnostic surface is a genuine
Core gap. Existing runtime discovery must remain strict.

### Publication-producer discovery

`pds_core.publication_compatibility` provides the corresponding strict
publication-producer profile, compatibility, discovery, and registry behavior
for `paper_data_suite.publication_producers`.

The same runtime-versus-diagnostic distinction applies.

**Conclusion:** bounded failure-isolating diagnostics for this Core-owned
provider contract are a genuine Core gap.

### Retained scans and route dispatch

Core already provides:

- `retain_source_scan(...)`;
- PDS2 parsing/identity;
- route registration;
- `dispatch_route(...)`;
- `dispatch_routes(...)`;
- ordered success/failure results; and
- generic failure/resolution metadata.

`dispatch_routes(...)` already performs ordered batch dispatch and isolates
expected per-request failures.

Core's accepted active scan contract explicitly does **not** decode images,
split/rasterize PDFs, detect QR pixels, interpret module records, write
module-owned evidence, or implement module Review UI.

Quillan's released intake documentation demonstrates the current boundary:
Quillan retains the source through Core, enumerates/rasterizes retained pages,
decodes raw QR text, asks Core to parse PDS2, creates ordered dispatch requests,
calls `dispatch_routes(...)`, and then integrates only Quillan-owned successful
outcomes.

**Conclusion:** #190's proposed batch dispatch/result layer duplicates an
existing Core capability. The actual unsolved layer is pre-dispatch physical
page/QR extraction, and moving that layer into Core would reverse an accepted
ownership decision and introduce imaging concerns. It is not justified for
Core 0.6.2.

### Grouping signals

Core 0.6.1's `grouping_signal_set_v1` contract, CSV conversion, immutable
exchange storage, digest binding, and roster/class diagnostics are complete.

**Conclusion:** grouping signals require no v0.6.2 changes and must not be
repurposed as readiness, attention, diagnostics, routing, or generic student
status.

## `pds doctor` conclusions

The expanded doctor specification is concrete consumer evidence, but it does
not make Core 0.6.2 a prerequisite for the doctor command itself.

The suite owns:

- Python and release qualification;
- environment-marker diagnosis;
- distribution/version comparison;
- `pip check`;
- manifest-to-installed entry-point metadata comparison;
- external prerequisite checks;
- diagnostic ordering;
- PASS/WARN/FAIL/SKIP;
- teacher-facing summaries/remediation; and
- overall health.

Core owns only Core facts consumed by doctor, such as workspace state, school
year, registry health, and validation of Core-defined provider contracts.

The doctor contract explicitly permits honest degradation. If an installed
Core/module combination has no shared readiness provider, the shell can report
that capability as unavailable/`SKIP`.

Therefore:

```text
pds doctor
```

is **not hard-blocked** on #189 or #191.

Those issues improve the fidelity and breadth of doctor results.

## Provider diagnostics: required runtime/health split

Core must preserve two distinct modes.

### Runtime registry construction

Purpose: build a registry that can be trusted for routing/publication work.

Expected behavior:

- load providers;
- validate exact contract/profile;
- reject duplicates/conflicts;
- fail closed when registry integrity cannot be established.

The existing discovery/registry APIs serve this role.

### Diagnostic inspection

Purpose: explain the installed Core-defined provider surface.

The missing diagnostic operation should preserve independent candidate
outcomes where safe.

A conceptual result should be able to represent:

```text
entry-point group/name/target
owning distribution, when determinable without import
load attempted: yes/no
load success/failure
callable/non-callable
provider call success/failure
returned profile valid/invalid
declared identity
identity mismatch
duplicate/conflict
Core contract compatibility
bounded safe error code/message
```

The API should distinguish metadata inspection from provider execution.

A metadata-only operation must not load optional module code merely to answer
which entry points are installed.

A deeper diagnostic operation may load/call a provider, but that behavior must
be explicit and failure-isolating.

This is the narrowed scope for #189.

## Readiness and attention: related but distinct contracts

The evidence is now sufficient to justify a shared neutral operations-provider
family.

Suite #16 explicitly requests bounded providers for:

- readiness;
- attention summaries;
- next actions; and
- diagnostics.

ScoreForm, Quillan, Concord, and Meridian each have planned doctor/readiness
work and separate attention work. Those downstream plans demonstrate that
readiness and attention are not synonyms.

```text
readiness:
  can this module operate correctly in this environment/context?

attention:
  is there teacher work in this module that currently needs attention?
```

The recommended #191 design is one neutral **provider family**, with distinct
optional capabilities/result types rather than one overloaded status object.

Core should define only the shared envelope/discovery/validation and
privacy-minimal structural types.

Modules determine:

- readiness facts;
- attention facts;
- module-local codes;
- safe labels;
- counts;
- domain context; and
- what owner-routed action is appropriate.

The suite determines:

- which installed providers to call;
- aggregation;
- ordering;
- teacher presentation;
- remediation/navigation UX; and
- whether an optional capability is shown as unavailable.

A conceptual operations profile may advertise optional callables such as:

```text
readiness provider
attention provider
```

with an owner-routed opaque action reference usable by returned results.

Exact public names, entry-point group, contract-version value, and field set
belong to the #191 implementation design. They are deliberately not fixed by
this audit.

The contract must not become a generic application registry or suite release
manifest.

## Diagnostic events: no Core contract justified for v0.6.2

The suite's doctor result types are shell-owned.

Suite #25 separately and explicitly owns the local diagnostic-event workflow,
including categories, relative paths, versions, stage outcomes, exception
summaries, retention, rotation, and prohibited default-log fields.

No current released sibling requires an independent cross-repository
persistent diagnostic-event wire format to perform Phase 1 work.

Module readiness/attention providers can return bounded neutral provider
results through #191; the suite can normalize its own local diagnostic records
without making Core own the local log format.

Therefore #192 should close as not planned for v0.6.2.

If multiple independent producers later need a persistent/exchange diagnostic
event contract outside the suite, open a new evidence-backed Core issue then.

## Mixed-module intake trace

The current end-to-end boundary is:

```text
teacher-selected source
  -> suite/module selects eligible file
  -> Core retain_source_scan
  -> retained bytes
  -> non-Core physical page enumeration/rasterization
  -> non-Core QR detection/decoding
  -> Core PDS2 parse
  -> ordered RouteDispatchRequest values
  -> Core dispatch_routes
  -> module-owned route handler/result integration
  -> module-owned evidence or Review workflow
  -> Core generic routing failure/resolution metadata where applicable
```

This trace exposes no missing Core batch dispatch abstraction.

The real cross-module integration question is physical page/QR extraction.
Core's accepted active scan contract explicitly assigns payload extraction to
modules and excludes image decoding/PDF splitting.

The suite may own the integrated physical extraction layer for its mixed-intake
workflow, or a future separately justified neutral extraction package could be
considered. Neither conclusion justifies silently expanding Core #190.

Therefore #190 should close as not planned for Core 0.6.2.

## Backup analysis

Suite #10 requires a non-overwriting local backup with a deterministic manifest,
source/destination containment checks, free-space checks, exclusions, and
protection against recursive backup.

Suite #11 requires byte-inventory/hash verification and restore to an explicit
alternate location, followed by a separate workspace-selection action.

Those are shell responsibilities.

A correct whole-workspace backup must preserve unknown/future module trees; it
cannot depend on Core understanding every module's canonical paths.

The shell can:

1. resolve the workspace through Core;
2. perform generic path-containment/free-space safety checks;
3. consult existing Core registry status for known Core locks/temporary
   artifacts;
4. optionally consult module operations/readiness providers when available;
5. snapshot the workspace bytes according to suite backup policy; and
6. verify its own backup manifest/hashes.

Core already exposes `workspace_baseline_dirs(...)` for initialization and
bounded registry lock/temporary-artifact status for Core registry health, but
neither should be treated as a complete backup inventory.

A new "authoritative Core workspace inventory" would create a dangerous
implication that anything not named by Core can be omitted. That conflicts with
opaque backup custody and future module compatibility.

Unsafe backup destinations are generic filesystem containment concerns owned by
the shell, not Core semantics.

Therefore #193 should close as not planned for this backup design.

If a future feature introduces selective/partial semantic backups, that feature
must establish an owner-contributed inventory contract rather than hard-coding
sibling storage knowledge into Core.

## Detailed dispositions for #186–#196

### #186 — bounded shared class and roster management facade

**Disposition: merge into #187; close #186 as a separate implementation issue.**

Evidence:

- class folder and class metadata operations already have public Core APIs;
- roster validation, storage, and mutations already have public Core APIs;
- suite #9 explicitly says to compose existing Core services;
- no consumer currently needs a generic all-purpose service layer; and
- the one demonstrated missing safety abstraction is complete roster import
  preview/diff/stale-guard semantics.

A generic facade would mostly rename existing calls and increase public surface
without adding authority or safety.

Any application-level roster operation that adds real safety belongs in #187.

Finding: `scope-reduction`, `existing-capability`.

### #187 — roster import preview, diff, and guarded commit

**Disposition: keep and rewrite narrowly around the demonstrated gap.**

This is a genuine Core-owned capability because the diff depends on Core's
student identity and roster semantics.

Minimum behavior:

- parse/validate the complete candidate roster before mutation;
- require the candidate `class_id` to match the target class;
- compare records by durable `student_id` only;
- preserve all accepted extra fields;
- report additions, changes, removals, and unchanged records deterministically;
- treat changed records as complete record changes, not fuzzy name edits;
- represent the current-roster baseline with a stable fingerprint or equivalent
  expected-state token;
- require explicit commit;
- re-read/revalidate current state at commit;
- reject stale preview/commit if current roster no longer matches the reviewed
  baseline;
- write the complete accepted roster atomically; and
- never infer identity from names.

Conceptual public shape:

```text
plan_roster_import(...)
  -> RosterImportPreview

commit_roster_import(..., expected_current_state=...)
  -> committed Roster / typed conflict
```

Exact names are follow-up design details.

Finding: `implementation-gap`.

### #188 — school-year and Academic Period setup planning

**Disposition: close as not planned for v0.6.2.**

Academic Period validation, transition checking, immutable revisions, explicit
current pointers, write locks, and expected-revision conflict protection
already exist.

Active school-year state already has explicit open/close operations and atomic
writes. The current setup workflow does not demonstrate a need for a long-lived
Core planning object.

The shell can review proposed teacher input without owning the validation, then
invoke the appropriate Core service.

A future school-year expected-state/CAS enhancement may be reasonable if a
concrete concurrent/long-lived-preview consumer appears, but it is not a Phase
1 requirement today.

Finding: `existing-capability`, `deferred-unproven`.

### #189 — installed module/publication-producer inventory diagnostics

**Disposition: keep, but narrow substantially.**

Remove generic installed-application/package/release inventory from this issue.
The suite already owns those facts.

Keep only failure-isolating diagnostics for **Core-defined provider contracts**,
initially routing-module and publication-producer providers.

Do not weaken current fail-closed runtime registry construction.

Provide a separate diagnostic path that can:

- inspect candidate metadata without workspace reads;
- avoid loading provider code for metadata-only questions;
- optionally perform explicit isolated provider load/call/validation;
- return one bounded outcome per candidate;
- preserve duplicate/conflict information; and
- expose no student/workspace domain records.

#191 may reuse the same diagnostic principles for a future Core-defined
operations-provider family.

Finding: `implementation-gap`, `scope-reduction`.

### #190 — additive batch scan-intake planning/result models

**Disposition: close as not planned.**

Core already has ordered batch dispatch/results via `dispatch_routes(...)`.

The actual missing integrated layer is physical page enumeration/rasterization
and QR extraction before PDS2 parsing. Core's accepted active scan contract
explicitly excludes that work.

Do not add redundant batch wrappers or reverse the scan ownership decision
inside a minor release.

Suite #17 can remain Core-backed by using retention, PDS2 parsing, and dispatch
while owning the integrated discovery/planning presentation.

Finding: `existing-capability`, `ownership-correction`.

### #191 — shared module-attention provider protocol

**Disposition: rewrite as a neutral module-operations provider family.**

The original attention-only title is now too narrow. Suite #16 and downstream
module tickets provide real cross-repository evidence for both readiness and
attention.

Retain distinct optional capabilities/result types:

```text
readiness
attention
owner-routed next action
```

Diagnostics should mean bounded provider diagnostics/readiness information, not
a persistent logging contract.

Core owns:

- neutral contract/version;
- safe structural models;
- discovery/validation;
- capability advertisement;
- privacy constraints; and

## Interface sketches for surviving Core gaps

These sketches define ownership and safety, not final API names.

### Guarded roster import

```text
input:
  workspace root
  target class_id
  candidate roster bytes/path or validated Roster
  optional current-state expectation

preview:
  validated candidate
  deterministic additions
  deterministic changed records
  deterministic removals
  deterministic unchanged count/identities
  current baseline fingerprint/state token
  no write

commit:
  re-read current canonical roster
  compare against reviewed baseline
  fail on stale state
  atomically write full accepted roster
  return durable result

errors:
  invalid candidate
  class mismatch
  duplicate student_id
  current roster unreadable
  stale preview/conflict
  write failure
```

The fingerprint must bind the actual canonical current state strongly enough to
detect a change between preview and commit. The implementation issue should
choose whether that is canonical-byte SHA-256 or another exact expected-state
representation.

### Core-defined provider diagnostics

```text
metadata inspection:
  no workspace required
  no provider load required
  stable candidate ordering
  entry-point identity/target/owner where available

isolated validation:
  explicit provider load/call
  one bounded result per candidate
  safe failure code/stage/message
  valid returned profile when successful
  duplicate/conflict reporting
  Core contract compatibility
```

Runtime registry construction remains separate and fail-closed.

### Module-operations provider family

```text
profile:
  Core contract version
  module/provider identity
  advertised optional capabilities

readiness capability:
  bounded module-owned readiness results
  privacy-minimal shared fields
  no raw student evidence
  provider-local failure isolation

attention capability:
  bounded module-owned summary/count/state
  safe optional class/work context
  opaque owner-routed next action
  no raw domain records

suite:
  discovers/calls providers
  aggregates
  presents
  decides shell remediation/navigation
```

The follow-up must decide the smallest shared request context. It should not
pass an entire module store or force every provider to read student records.

## Discovery safety classification

Every future provider API must state which boundary it crosses:

| Operation | Loads optional code? | Reads workspace? | Executes provider? |
| --- | ---: | ---: | ---: |
| inspect installed distribution metadata | no | no | no |
| inspect entry-point metadata | no | no | no |
| load entry-point object | yes | no | no provider call yet |
| call profile provider | yes | no by contract unless explicitly documented | yes |
| request module readiness | yes | possibly bounded context | yes |
| request module attention | yes | module decides bounded reads | yes |
| route a page | yes | yes | yes |

Do not describe these operations with one ambiguous verb such as "discover."

## Privacy findings

The surviving provider work can remain privacy-minimal.

Shared readiness/attention/provider diagnostics must not require:

- student names;
- student answers;
- scores or percentages;
- writing bodies;
- teacher feedback;
- behavior narratives;
- portfolio content;
- raw scans;
- QR payload bodies;
- grouping-signal values;
- whole module records;
- credentials; or
- unrelated machine/environment dumps.

Opaque owner-routed action references are preferable to copying domain state
into Core or the suite.

Core registry findings already constrain paths to safe workspace-relative forms
where applicable; suite presentation should preserve that discipline.

## Grouping-signal isolation

Nothing in the surviving v0.6.2 scope changes the accepted relationship:

```text
Meridian -> Core grouping signal interchange <- Concord
```

Grouping signals are not:

- readiness results;
- attention results;
- diagnostic events;
- route metadata;
- backup inventory;
- launch metadata; or
- permanent learner classifications.

No grouping-signal schema or path change is justified by this audit.

## Cross-owner transaction boundary

The shell may preview, sequence, invoke, collect results, and stop after a
failure.

It must not claim rollback across unrelated Core/module writes unless an owner
provides a real correction/rollback/supersession mechanism.

The only new guarded transaction required by this audit is contained within
Core's own roster file: preview a complete replacement, bind the preview to
current state, and atomically replace that one canonical roster only if the
reviewed baseline is still current.

No suite-wide transaction manager is justified.
