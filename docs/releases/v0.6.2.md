# pds-core v0.6.2

**Release date:** August 21, 2026

**Status:** Supported additive Core 0.6 release after #196 post-merge qualification

PDS Core v0.6.2 adds guarded full-roster replacement, failure-isolating
provider diagnostics, and a neutral module-operations provider contract while
preserving the existing Core 0.6 routing, workspace, roster, standards,
Academic Period, academic-registry, publication, catalog, and grouping-signal
contracts.

The release is deliberately narrow. It supplies shared authority and neutral
integration contracts required by Phase 1 consumers without turning Core into
the Paper Data Suite shell or moving module-owned interpretation into Core.

```text

```

The existence of v0.6.2 does not require every existing Core 0.6 consumer to
change its dependency floor.

## Architecture boundary

The intended dependency direction remains:

```text
teacher
  -> Paper Data Suite shell
      -> public Core shared services
      -> installed module public services
```

Core owns neutral shared authority. The suite shell owns release composition,
orchestration, aggregation, launch UX, backup/restore, and teacher-facing
presentation. Modules own their domain facts, domain records, interpretation,
repair workflows, readiness meaning, attention meaning, and owner actions.

Core v0.6.2 does not add a generic suite application registry or make any Core
provider family proof of application launchability or suite qualification.

## Guarded full-roster import

The public `pds_core.roster_imports` service adds explicit review-before-write
full-roster replacement:

```python
plan_roster_import(...)
commit_roster_import(...)
```

A preview:

- validates the complete candidate roster;
- requires exact target `class_id`;
- uses `student_id` as the only student identity;
- reports deterministic additions, changes, removals, and unchanged IDs;
- returns an opaque current-state token; and
- returns an opaque candidate-state token.

Commit requires both exact reviewed tokens. It rejects a changed candidate or a
changed canonical roster rather than silently recalculating the reviewed state.
The write occurs under the same per-roster write coordination used by canonical
roster writes and installs the complete candidate atomically.

The operation has no force, overwrite, ignore-stale, or recompute-and-commit
bypass.

The direct noninteractive CLI exposes the same public service through:

```text
pds-core roster import-preview <class_id> <candidate_csv>
pds-core roster import-commit <class_id> <candidate_csv> \
  --expected-current-state-token <token> \
  --expected-candidate-state-token <token>
```

The guarded roster operation is intentionally CLI-only in Core. A suite shell
may provide a guided teacher workflow over the public service while Core
retains canonical roster authority.

## Failure-isolating provider diagnostics

`pds_core.provider_diagnostics` provides two deliberately separate operations:

```python
inspect_core_provider_entry_points(...)
diagnose_core_providers(...)
```

Metadata inspection enumerates Core-owned provider entry points without loading
optional provider code. Diagnostic evaluation loads and validates candidates
independently so one malformed optional provider does not hide unrelated
provider observations.

Diagnostics cover the three Core-owned provider families:

```text
paper_data_suite.modules
paper_data_suite.publication_producers
paper_data_suite.module_operations
```

Normal runtime registries remain strict and fail closed. Diagnostics do not
become suite package/version authority, launchability authority, or a
teacher-facing PASS/WARN/FAIL presentation policy.

## Module-operations provider contract

Core v0.6.2 defines the versioned neutral:

```text
paper_data_suite.module_operations
```

contract with:

```text
MODULE_OPERATIONS_CONTRACT_VERSION = "1"
```

The contract keeps two capabilities distinct:

```text
readiness
  whether a module can operate correctly for the supplied neutral context

attention
  bounded module-owned work that may need teacher attention
```

Core defines shared structure, discovery, validation, bounded invocation
results, and privacy-minimal owner-routed action references. Modules decide what
their own state means. The suite decides how results are aggregated and
presented.

The contract explicitly distinguishes provider absence, capability absence,
unavailable evaluation, successful evaluation, provider failure, and invalid
returned results. An absent operations provider is not automatically an
unhealthy module.

Released consumers are not required to implement this optional provider merely
because Core v0.6.2 defines it.

## Released-consumer qualification

Issue #195 added an exact, reusable qualification manifest and runner for every
released installable Core 0.6 consumer identified by the Phase 1 API audit:

| Consumer | Exact release | Expected Core-facing providers |
| --- | --- | --- |
| ScoreForm | `0.10.0` | routing, publication |
| Quillan | `0.9.0` | routing, publication |
| Concord | `0.2.0` | routing, publication |
| Meridian | `0.1.1` | none |
| Vitrine | `0.2.0` | none |

The fixture pins exact GitHub Release identities and authenticated SHA-256
values. The qualification runner creates an independent environment per
consumer, installs the supplied Core wheel beside the exact released consumer
wheel, runs `pip check`, verifies installed imports and public Core provider
contracts, and exercises documented CLI help/version behavior.

Provider absence is tested as an explicit expectation rather than treated as a
failure. None of the five released artifacts is required to expose
`paper_data_suite.module_operations` for v0.6.2 compatibility.

The v0.6.2 release audit must run that same qualifier against the exact candidate
wheel and repeat it against the exact wheel rebuilt from the final merged
release-preparation commit. The provisional wheel created during #195 is not a
release artifact and its hash is not release authentication.

See
[`../released_consumer_compatibility.md`](../released_consumer_compatibility.md)
for the exact qualification contract.

## Paper Data Suite handoff

Core release qualification and suite release qualification remain separate.

Core answers:

```text
Can exact released Core 0.6 consumers continue to use Core 0.6.2?
```

After this release, `Paper-Data-Suite/pds-paper-data-suite#38` separately
answers:

```text
Which exact Core artifact does the Paper Data Suite v0.1.0 composition qualify?
```

That downstream issue authenticates the published Core v0.6.2 wheel, updates
the suite compatibility manifest, migrates guided roster setup to Core's
guarded service where appropriate, and adopts other shared services only where
justified.

Core does not modify the suite compatibility manifest as part of this release.

```powershell
python -m pip check
pds-core --help

```

PDS Core release artifacts are distributed through GitHub Releases rather than
PyPI unless project policy is explicitly changed.

## Migration from v0.6.1

No workspace migration is required merely to install v0.6.2.

Installing or importing v0.6.2 does not automatically:

- replace a roster;
- discover or invoke optional module operations;
- create readiness or attention records;
- create a workspace;
- rewrite existing Core records;
- change grouping signals;
- change routing or publication state.

New behavior occurs only through explicit public API/CLI calls or explicit
provider discovery/invocation.

## Security and privacy

Release tests, compatibility fixtures, and examples use synthetic data only.
The new shared surfaces are intentionally bounded:

- roster-import tokens bind exact canonical/candidate roster state but callers
  treat them as opaque values;
- provider metadata inspection does not load optional provider code;
- normal diagnostic results do not expose raw traceback/environment dumps;
- module-operations notices and attention summaries are bounded and
  privacy-minimal;
- owner actions are opaque module-routed references rather than arbitrary
  commands, URLs, imports, or filesystem paths.

Do not commit or publicly post real rosters, student IDs, student work, grades,
scans, classroom records, credentials, or private school/district information.
See [`../../SECURITY.md`](../../SECURITY.md).

## Explicit non-goals

Core v0.6.2 does not add:

- a Paper Data Suite release manifest;
- a generic application or launch registry;
- suite launch orchestration;
- doctor PASS/WARN/FAIL/SKIP presentation or remediation;
- backup/restore;
- a Core-wide diagnostic-event store;
- diagnostic retention/rotation policy;
- another batch scan-dispatch engine;
- PDF rasterization;
- image decoding;
- QR image extraction;
- module-specific readiness or attention semantics;
- module dashboards;
- suite-wide transactions;
- new grouping-signal semantics;
- Grade/proficiency policy;
- mandatory sibling dependencies;
- mandatory module-operations providers.

## Release artifacts and qualification boundary

The normal v0.6.2 distribution artifacts are:

```text
pds_core-0.6.2-py3-none-any.whl
pds_core-0.6.2.tar.gz
SHA256SUMS.txt
```

The release-preparation PR may produce candidate artifacts, but those bytes are
not automatically final. After the preparation PR is squash-merged, release
qualification rebuilds the wheel and sdist from the exact merge commit,
recomputes their hashes, reruns installed acceptance and the five-consumer
matrix, and only then authorizes tag `v0.6.2` and GitHub Release publication.

If an artifact is rebuilt after qualification, its earlier hash is invalid as
release evidence and the rebuilt bytes must be authenticated and qualified
again.
