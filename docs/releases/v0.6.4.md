# pds-core v0.6.4

**Release date:** September 30, 2026

**Status:** Backward-compatible Core 0.6 path-safety patch prepared by #226

PDS Core v0.6.4 bounds newly created retained-source filenames and newly generated
`source_scan_id` values so external scanner filenames cannot consume an unbounded
amount of the canonical workspace path budget.

The patch preserves the existing Core 0.6 active-scan layout, custody semantics,
routing contracts, Scan Review schemas, and stored provenance. Existing retained
sources are not renamed or migrated.

| Item | Value |

Existing Core 0.6 consumers do not need to raise their dependency floor merely
because v0.6.4 exists.

## Bounded retained-source writer

For newly retained scans, Core keeps the established timestamp/content-digest
shape while applying a fixed budget to the source-derived component.

Ordinary sanitized source stems up to 64 characters retain the established
human-readable serialization. Longer stems are replaced by a bounded
`scan_<16-hex-filename-digest>` component.

The resulting writer guarantees:

```text
maximum newly generated retained filename: 107 characters
maximum newly generated source_scan_id:     107 characters
```

The original selected filename remains preserved exactly in:

```text
RetainedSourceScan.source_filename
```

The canonical retained-source location remains:

```text
<workspace>/scans/source/YYYY-MM-DD/<retained source>
```

The filename bound is independent of class, module, and work identities and no
longer grows with arbitrarily long external source stems.

## Legacy reader compatibility

The writer bound is prospective. Readers intentionally remain more permissive.

Existing Core 0.6 retained filenames and `source_scan_id` values remain valid,
even when they are longer than the new writer maxima. Core does not automatically:

- rename an existing retained source;
- rewrite a retained-source relative path;
- rewrite a source-scan ID;
- rewrite Scan Review failure or resolution metadata;
- rewrite route, result, registry, publication, or module records; or
- scan the workspace for legacy filenames.

A frozen Core 0.6.3-style legacy fixture verifies that over-limit historical
provenance remains readable and round-trips through routing failure and Scan
Review resolution metadata unchanged.

No workspace migration is required.

## Custody and repeated-intake semantics

The path-safety change does not weaken retained-source custody. Core continues to:

- hash the selected source bytes;
- create the retained destination exclusively;
- hash the copied bytes again;
- detect source mutation during retention;
- clean up incomplete copies where safe;
- require the retained destination to stay beneath the workspace root; and
- leave the external source unchanged.

Identical bytes retained at distinct intake timestamps remain distinct intake
events. A true exact destination collision remains a non-overwriting error.

## Windows path-policy boundary

Issue #226 was opened after a physical ScoreForm workflow produced a 281-character
retained path beneath a legitimate 119-character workspace root. Poppler/pdf2image
failed before page discovery even though Windows reported:

```text
LongPathsEnabled = 1
```

Core v0.6.4 therefore treats Windows long-path support as defense in depth, not
as an application-level storage contract. Automated Windows qualification reads
the setting before and after installed acceptance and fails if qualification
changes it. Core does not modify the registry.

The deterministic regression fixture demonstrates the same path geometry while
the bounded writer produces a substantially shorter canonical leaf.

## Installed acceptance

Release qualification builds both:

```text
pds_core-0.6.4-py3-none-any.whl
pds_core-0.6.4.tar.gz
```

and verifies the exact artifacts before publication.

The wheel is installed in a clean environment outside the source checkout. The
source distribution is installed separately in another clean environment. Both
installed distributions run the v0.6.4 acceptance surface, including the bounded
retained-source contract.

Issue #226 additionally runs dedicated Windows installed-wheel qualification
against deliberately long source names and the frozen Core 0.6.3 provenance
fixture without changing `LongPathsEnabled`.

## Migration from v0.6.3

No workspace migration is required merely to install v0.6.4.

Existing retained scans keep their current filenames, paths, IDs, and bytes.
Only newly retained scans use the bounded writer policy.

No automatic rewrite of Scan Review, result, routing, registry, publication, or
module data occurs.

## Release artifacts and qualification boundary

The normal v0.6.4 release artifacts are:

```text
pds_core-0.6.4-py3-none-any.whl
pds_core-0.6.4.tar.gz
SHA256SUMS.txt
```

Candidate artifacts produced on the release-preparation branch are not final
release evidence. After the release-preparation PR is squash-merged, the wheel
and sdist must be rebuilt from the **exact merge commit**, rehashed, and all
release gates rerun before tag `v0.6.4` and GitHub Release publication.

If artifact bytes are rebuilt after qualification, earlier hashes no longer
qualify those bytes.

## Security and privacy

The bounded retained filename is intentionally infrastructure-oriented. Long
source names are compacted using a bounded digest-derived component rather than
copied wholesale into the filesystem leaf. The exact original filename remains
available in structured provenance.

Qualification fixtures are synthetic. Do not commit real student scans, rosters,
IDs, grades, classroom records, credentials, or private district data.
