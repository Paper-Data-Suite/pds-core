# pds-core v0.6.1

**Release date:** August 18, 2026

**Status:** Supported pre-1.0 Core release

Core v0.6.1 adds the neutral `grouping_signal_set_v1` interchange while
preserving the existing Core 0.6 routing, roster, standards, Academic Period,
academic-registry, publication, catalog, and audit surfaces.

The release does not implement Meridian academic interpretation or Concord group
planning. It provides the shared, producer-neutral contract between them.

## Architecture summary

The grouping-signal dependency direction is:

```text
optional producer
      |
      v
     Core
 grouping_signal_set_v1
      |
      v
optional consumer
```

The initial planned integration is:

```text
Meridian -> Core -> Concord
```

Neither Meridian nor Concord is required to author, parse, validate, store, or
diagnose a conforming grouping signal through Core.

## Grouping-signal capabilities

### Typed contract and canonical JSON

`GroupingSignalSet` represents one immutable class-scoped snapshot of contextual
ordinal bands. Version 1 uses strict exact fields, explicit source provenance,
independent dimensions, exact `student_id` identity, and deterministic ordering.
Bands are ordinal planning signals from `1..N`; they are not Grades,
percentages, proficiency labels, permanent ability labels, or group assignments.

Canonical JSON is UTF-8, two-space indented, LF-terminated, and byte-exact.
Semantically equivalent but byte-different canonical-wire input is rejected.

### Human-editable CSV

`grouping_signal_csv_v1` represents exactly one selected dimension using a
`student_id,band` table plus a fixed metadata preamble.

A complete one-dimension signal can round-trip losslessly. A selected dimension
from a multi-dimension source is marked `dimension_projection` and cannot become
a standalone signal under the source identity; conversion requires a new
explicit `signal_set_id` and aware `created_at`.

CSV is an editing/interchange representation. Canonical JSON remains the
integrity authority.

### Immutable exchange storage

Core stores exact canonical bytes at:

```text
exchange/grouping-signals/<class_id>/<signal_set_id>.json
exchange/grouping-signals/<class_id>/<signal_set_id>.json.sha256
```

The sibling digest binds the exact canonical JSON bytes with SHA-256. Identical
replay is idempotent without rewriting. Reuse of the same identity for different
canonical contents is a conflict.

There is no `latest`, `current`, `active`, revision, supersession, or in-place
update concept for version 1 grouping signals.

### Exact class/roster diagnostics

Workspace-aware diagnostics compare a structurally valid signal with one exact
Core class roster. They distinguish:

- target-class students;
- exact IDs found in other canonical class rosters;
- IDs not found in any completely scanned canonical roster;
- target-roster members missing from each dimension; and
- target-matched per-band counts.

Diagnostics do not use names, email addresses, fuzzy matching, automatic
remapping, or missing-band completion. Malformed participating roster state
fails the diagnostic operation rather than producing an uncertain identity
classification.

## Standalone and downstream fixtures

The release includes a separately authenticated synthetic fixture asset:

## Migration from v0.6.0

No migration is required merely to install v0.6.1. Existing Core 0.6 workspace
records retain their meanings and locations.

Grouping-signal namespaces are created only by explicit grouping-signal write
operations. Installing or importing v0.6.1 does not create signals, classes,
rosters, exchange state, Groups, or Grade state.

A consumer that begins using the grouping-signal API should change its minimum
constraint to:

```text
pds-core>=0.6.1,<0.7
```

and use only the public Core model/CSV/storage/diagnostic APIs rather than
recreating their wire or persistence rules.

## Security and privacy

Every populated grouping signal is teacher-restricted educational data because
it contains class identity, student IDs, relative planning signals, and
provenance even though raw academic values are excluded.

Do not put grouping-signal contents in:

- public examples containing real identities;
- logs or crash reports by default;
- PDS2 payloads or route registrations;
- packet metadata;
- AcademicResult manifests;
- Publication Records.

Do not commit or publicly post real rosters, student IDs, scans, classroom
records, private school/district material, or credentials. Release fixtures use
synthetic identities only. See [SECURITY.md](../../SECURITY.md).

## Non-goals and known limitations

Core v0.6.1 does not implement:

- Grade or proficiency calculation;
- evidence/attempt selection;
- academic band derivation or tie policy;
- automatic signal generation/export;
- GroupPlan lifecycle;
- grouping algorithms;
- Groups or GroupMemberships;
- SIS synchronization;
- cloud/hosted storage;
- signed or secret-backed tamper authentication.

The `.sha256` sidecar detects accidental mutation and stale/corrupt bytes; an
actor with arbitrary local filesystem write access could deliberately replace
both the JSON and its sidecar.
