# pds-core v0.6.0

**Release date:** August 3, 2026

**Status:** Supported pre-1.0 Core release

Core v0.6.0 provides the shared contract.
It does not complete sibling-repository integration or implement Meridian.

Pre-1.0 releases may make intentional breaking changes. Unless documented
otherwise, only the latest supported minor line receives fixes.

## Architecture summary

This release implements accepted typed publication-registry and hierarchical
Academic Period architecture. Producers retain authoritative native records,
write immutable contract-versioned manifests, explicitly register eligible
academic work, and publish exact manifest revisions. Core preserves immutable
registration/publication/withdrawal history and exact SHA-256 bindings. Its
SQLite catalog is disposable discovery state. Consumers reload canonical
records and producer bytes before applying authorization and consumer-owned
grading or reporting policy.

Academic-result and intervention publications remain distinct. Intervention
data requires no Academic Work Registration and does not become a Score,
standards rating, or Grade. PDS2 page routing remains a separate surface.

## Notable changes since v0.5.0

### Academic Periods

- Added `AcademicPeriodRef`, `AcademicPeriod`, and immutable revisioned
  `AcademicPeriodCalendar` models with strict serialization.
- Added school-year-qualified identity, inclusive dates, six period types,
  explicit lifecycle, hierarchy validation, deterministic sibling ordering,
  overlapping structures, and transition validation.
- Added canonical revision storage with atomic explicit current pointers,
  expected-revision protection, exact reference resolution, and hierarchy/date
  queries.

### Academic Work Registration

- Added immutable `academic_work_registration` revisions keyed by complete
  `ModuleWorkRef`, with producer contract version, title snapshot, work kind,
  intent, lifecycle, timestamps, and source-record references.
- Added canonical revision history and explicit current pointers.
- Added idempotent create/replay and expected-revision update services with
  structured disposition and partial-success state.

### Publication registry and compatibility

- Added typed immutable `academic_result_set` and `intervention_record_set`
  Publication Records plus separate immutable withdrawals.
- Added shared academic and intervention capabilities, stable record-set
  series identity/revisions, explicit supersession, exact replay, contradiction
  detection, and canonical retrieval.
- Added workspace-relative POSIX manifest containment, regular-nonsymlink file
  verification, and exact SHA-256 byte binding without parsing producer data.
- Added publication producer compatibility models, evaluation, explicit
  registries, and entry-point discovery through
  `paper_data_suite.publication_producers`.
- Corrected profile validation so only producers supporting
  `academic_result_set` require Academic Work contract versions;
  intervention-only profiles may use an empty set.
- Added synthetic ScoreForm, Quillan, Concord, and Portia producer-contract
  fixtures and compatibility tests. Fixtures are not production integrations.

### Catalog, audit, and CLI

- Added the nonauthoritative `registry/catalog.sqlite` catalog with atomic
  complete rebuild, canonical source inventory/snapshot, schema/application
  identity checks, and typed deterministic queries.
- Added catalog states `current`, `series_heads`, `historical`, `withdrawn`,
  and `all`.
- Added bounded registry validation across periods, registrations,
  publications, manifest bytes, producer profiles, catalog, and locks.
- Added dry-run catalog repair and fingerprint-protected lock clearing.
- Added text and stable JSON-envelope output, strict warning handling, and exit
  codes `0`, `1`, and `2` for the academic command surface.

### Standards CLI and menu

- Added atomic ordered standard-definition batch addition.
- Added atomic profile membership add/remove and metadata-preserving set
  operations.
- Added shared presentation-independent transformations used by both direct
  CLI and teacher menu workflows, completing the post-v0.5 CLI/menu parity
  work included in this release history.

## Migration from v0.5

Downstream packages should update to:

```toml
dependencies = ["pds-core>=0.6,<0.7"]
```

Retain explicit routing and serialized-contract compatibility. Decide whether
the module is a publication producer; define real producer, manifest,
record-set, and source-record contracts; expose the publication entry point
only after implementation; explicitly register academic work; publish
immutable manifests through Core services; and add producer-owned integration
tests.

Upgrading does not create calendars or periods, register work, generate
manifests, publish records, build the catalog, crawl producer work, assign
Grade items to periods, calculate Grades, or repair state. New namespaces are
created only by explicit operations:

```text
settings/academic_periods/
registry/work/
registry/publications/
registry/withdrawals/
registry/catalog.sqlite
registry/.locks/
```

There is no previous catalog migration; the catalog is derived and should be
rebuilt. Use the [recovery guide](../academic_registry_recovery.md) for orphan
revisions, invalid pointers, publication corruption, missing manifests, digest
mismatches, and locks.

## Known limitations

- Core does not parse or normalize producer manifests.
- Core does not implement Grade, proficiency, attempt/evidence selection,
  period membership, reporting, authorization, or Meridian.
- No calendars, registrations, publications, or catalog are created on upgrade.
- Canonical pointer or publication-series corruption requires separately
  reviewed recovery; catalog rebuild cannot repair it.
- Missing producer profiles reduce compatibility evidence but do not change
  canonical state.
- Sibling publication integrations and their dependency updates remain owned
  by those repositories.
- Core remains pre-1.0 and does not promise permanent API stability.

## Security and privacy

Producer manifests and native records may contain sensitive educational data.
Keep them under deployment-controlled permissions and never post them, real
student/roster/scan data, credentials, or private school information publicly.
Discovery does not grant authorization. See [SECURITY.md](../../SECURITY.md).
