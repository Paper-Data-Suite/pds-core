# pds-core v0.6.5 — release candidate notes

**Target version:** v0.6.5 (Core #229)  
**Release date:** Not yet set  
**Status:** Candidate planning; not yet tagged, merged or released.

PDS Core v0.6.5 will extend `pds_core.publication_compatibility` with optional producer-declared reader-contract metadata. It retains the existing Core 0.6 profile, publication, workspace, Academic Work, source-record and capability contracts without migration or changed compatibility decisions.

## Reader-contract metadata

`PublicationReaderSupport` is a frozen descriptor of a producer's **manifest contract version**, canonical **Python distribution name** and independently versioned **reader contract**. It is an optional trailing field on `PublicationContractSupport`, defaulting to an empty tuple. Exact lookup uses `lookup_publication_reader_support(profile, publication_kind, manifest_contract_version)` and returns one declared row or `None`.

Core validates declarations and exposes metadata, but does not import readers, execute them, interpret producer manifests, authorize evidence access, select consumers, or infer reader contracts from installed distribution versions. A missing declaration remains valid and does not change publication compatibility.

Academic results retain existing Academic Work Registration semantics. `intervention_record_set` supports the same metadata without Academic Work Registration. Portia #66 is a future consumer/producer integration, not a released Core publication producer.

## Producer/consumer handoff

Meridian #111 and Vitrine #103 can adopt the same declaration API after independently qualifying actual producer reader contracts. Consumer-side legacy allowlists, adapter compatibility, access checks and grading/portfolio projection policies remain consumer owned. Future Portia #66 may use the same metadata for privacy-minimized intervention publication without adding academic-result assumptions.

See [reader metadata contract](../publication_reader_contract_metadata.md) and [Core #229 release plan](../validation/issue-229-v065-release-plan.md).

## Release compatibility and evidence

Core #229's implementation passed local focused/full regression, strict mypy and pre-release installed wheel smoke before release activation. These are **not** final v0.6.5 release assertions. The active candidate must pass a separately qualified v0.6.5 wheel and source distribution, exact Core-only installed acceptance and an authenticated matrix of six currently released consumers. Their exact wheel digests are pinned in the *new* v2 fixture as a frozen v0.6.5 qualification snapshot, not as Core module dependencies or a requirement to update Core when a sibling module releases. Core 0.6.4 historical release fixtures and documentation remain unchanged.

There is no workspace migration, and installed downstream applications need not opt into reader metadata until their own contract support is reviewed and released.
